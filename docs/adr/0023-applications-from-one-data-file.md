# 0023: Applications from one data file; CLI tools via mise; Nix from nixpkgs-unstable

**Context:** An Application was listed in up to seven places: the Profile lists in `.chezmoi.toml.tmpl`, an identifier table in each of the Brewfile, apt, winget and mise templates, the package list in the Nix module (ADR 0021), and the expected IDs in both assert scripts. The CLI tools also came from a different source per OS — mise on Linux (ADR 0012), Homebrew on macOS, winget on Windows with mise exceptions (ADR 0013, 0017, 0019), nixpkgs on the NixOS hosts — so versions differed between machines. A measurement on 2026-11-12 compared each source with the upstream release: mise's aqua backend (the upstream GitHub release) and Homebrew matched it for every tool, winget lagged on lazygit, fd and resvg, nixpkgs-unstable lagged by at most a patch release on two tools, and the stable nixos-26.05 lagged on 13 of 17 tools by up to half a year. Nothing kept the mise and Nix paths aligned or current.

**Decision:** One data file, `applications.toml` in `home/.chezmoidata/`, describes every Application once: CLI tools, GUI apps, system packages and the node/python runtimes, each with its Profiles, its source per platform (`mise`, else `brew`/`apt`/`winget`/`flatpak`), an optional exact-version pin, its nixpkgs attribute (or a flake input or module option for the special cases), and optional OS/architecture restrictions. Bootstrap Packages stay in the bootstrap scripts. Every consumer reads the file and filters by Profile, OS and architecture itself: the manifest templates, the mise config template, `.chezmoiignore`, the assert scripts and the Nix module (`builtins.fromTOML`). The chezmoi config template cannot read `.chezmoidata`, so it keeps only the Profile prompts and no longer holds Application lists.

On every chezmoi Target, a CLI tool with a mise backend is installed by mise, at `latest` unless pinned; Homebrew, apt and winget keep the GUI apps and the Applications mise cannot install (zsh, file, unzip, the build tools, and per platform whatever has no build there, e.g. tmux on Windows where psmux stands in, resvg on Windows). A `mise.lock` covering all Applications and all platforms in use is generated in CI with `mise lock --global --platform …`, kept in the Source Dir, deployed next to the global mise config and installed with `mise install --locked`.

The NixOS hosts keep consuming the repo as a flake input, with no chezmoi on the host (ADR 0021 stands). The module takes every Application it can from nixpkgs, defaulting to the `nixpkgs-unstable` input for all of them (a consumer can pass its own nixpkgs), and installs GUI apps for Profiles that list them. No mise and no nix-ld on these hosts.

A scheduled workflow bumps `mise.lock` (pins untouched) and the `nixpkgs-unstable` input in one PR; CI compares each Application's version in `mise.lock` with nixpkgs-unstable and warns on a minor, fails on a major difference.

We considered keeping Homebrew and winget for the CLI tools on macOS and Windows (ADR 0012's position): rejected, since mise is never behind them and one source per tool on every Target is what makes the versions comparable. We considered mise with nix-ld on the NixOS hosts for exactly equal versions: rejected, the hosts stay Nix-native (binary cache, rollback) and nixpkgs-unstable is close enough. We considered pinning every tool in the data file: rejected, tools should stay current; the lockfile gives reproducibility without hand-edited versions.

**Consequences:** Adding an Application is one edit in the data file (plus the lockfile refresh CI does). On macOS and Windows the CLI tools leave the Brewfile and the winget manifest; on Linux tmux, cmake, 7zip and jq leave apt for mise. Local `mise upgrade` no longer updates anything: only `mise lock --global` writes the global lockfile, so updates arrive through the bump PR and `chezmoi update`. A tool missing from `mise.lock` fails `mise install --locked`, so CI checks the lockfile against the data file. One tool mise cannot install still fails the whole `mise install`, so OS/architecture restrictions must be kept accurate (today: delta has no Intel-Mac build, resvg none for linux-arm64 or Windows, tmux none for Windows). `latest` resolves through mise's version cache and can trail a fresh release by about a day. On the NixOS hosts the ADR 0013 pins are not applied: Neovim and tree-sitter come from nixpkgs-unstable, and the drift report shows the difference. This supersedes the installation path of ADR 0008 and ADR 0012, 0017 and 0019 (mermaid-cli was removed, issue #34), and amends ADR 0006, 0013 and 0021.

**Update (issue #28):** two more platform gaps on Windows. eza has no windows-arm64 build, so Windows on ARM keeps it on winget; for the other tools aqua installs the x64 build there, which runs under emulation. ImageMagick stays on winget on Windows: its conda build is lockable for windows-x64 but has never been run there, and yazi's image previews depend on it.

**Update (issue #29):** tmux, cmake, 7zip and jq move to mise on Linux and macOS; tmux comes from `aqua:tmux/tmux-builds` (static builds, none for Windows). On Windows cmake and jq follow, while 7-Zip stays on winget: its release ships only the standalone `7za` there, not the `7z.exe` yazi and the PATH fix in `run_after_set-yazi-env-windows` expect.

**Update (issue #30):** the lockfile covers six platforms (linux, macos and windows, each x64 and arm64) and is generated per platform for exactly the tools `mise_os`/`mise_arch` allow there, since `mise lock` aborts on a tool that cannot resolve for a platform (conda ImageMagick on windows-arm64). Locking every platform surfaced one more gap: eza publishes no macOS builds, so Macs keep it on Homebrew. The lockfile is generated on Linux, never on a NixOS host, where mise defaults to compiling python and writes a NixOS-only python entry. `.github/scripts/mise-lock.sh` generates it (CI: the `mise lock` workflow) and checks it (`--check`, the `mise-lock` CI job).
