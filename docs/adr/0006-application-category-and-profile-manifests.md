# Introduce Application category with profile-driven manifests, retire per-app GUI prompts

Bootstrap Package today covers `git`, `mise`, Docker, `pwsh`, and `psmux` — a mix of true chezmoi prerequisites and general tooling that happens to live in the same `run_once_before_install-packages.*` scripts, installed unconditionally regardless of Profile. We're narrowing Bootstrap Package back to its strict definition — only what's needed before anything else can run: `git`, `mise`, and the platform's own package manager where it isn't preinstalled (Homebrew on macOS; `apt` and `winget` already ship with their OS) — and introducing a new category, **Application**, for everything else a machine needs, including GUI apps (wezterm, VS Code, Zed, Windows Terminal, iTerm2) that today only get their config deployed while their install is assumed, never verified.

Applications are declared once per Profile, in a single platform-agnostic list (`[data.applications]` in `.chezmoi.toml.tmpl`). That list is the sole source of truth driving both which entries render into each platform's package-manager-native manifest (`Brewfile`, `apt-packages.txt`, a winget manifest — one file per platform, each with its own package identifier per app, and simply no entry where an app doesn't apply to that platform) and which GUI configs `.chezmoiignore` deploys, so the two can't drift apart the way two independently-maintained flags would. Manifests install via `run_onchange_` rather than `run_once_`, so an edit to the app list reaches already-provisioned machines on their next `chezmoi apply`, not only fresh installs.

We considered a custom data-driven package abstraction (our own schema resolving package names across managers) instead of native manifests, and a runtime fallback between package managers per app when a package isn't available on the preferred one. Rejected both: native tooling (`brew bundle`, `winget import`) already solves manifest installation and idempotency better than a hand-rolled version would (the same reasoning as ADR-0001, applied one level down), and a silent fallback risks installing the wrong package on a name collision between managers. Each app is assigned to exactly one manager per platform, decided by us when the app is added, not resolved at runtime. Homebrew-on-Linux, Fedora/Arch Application support, and `mise`-managed language runtimes are deliberately out of scope until a concrete need appears.

**Consequences:** the existing per-app GUI config prompts (`weztermConfig`, `vscodeConfig`, `zedConfig`, `windowsTerminalConfig`, `iterm2Config`, added in ADR-0004) are removed — Profile alone decides now, with no per-machine override. Two machines on the same Profile that need different Applications require a new, explicit Profile (e.g. `personal-laptop` vs `personal-desktop`) rather than an opt-out flag; accepted because that keeps app sets reproducible and visible in the diff instead of hidden per-machine state — Profile variance will grow. An app missing a manifest entry on a given platform fails silently, the same convention already used for iTerm2/Windows Terminal being absent outside their one platform; no CI check enforces cross-platform manifest coverage, since `ci.yml` deliberately verifies only the rendered file tree, not script side effects.
