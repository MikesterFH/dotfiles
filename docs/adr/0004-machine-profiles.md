# Introduce machine Profiles (personal / dev / dev-server) as a new deployment axis

`.chezmoi.toml.tmpl` today prompts unconditionally for all three git identities (`personal`, `work`, `client`) and every managed GUI config (wezterm, VS Code, Zed, Windows Terminal, iTerm2) gets deployed to every machine, regardless of what that specific machine is for. We're adding a `profile` prompt (`promptChoiceOnce`, values `personal` | `dev` | `dev-server`) that scopes which git identities get prompted/generated, and, for `personal`/`dev`, which GUI configs get deployed via a per-app opt-out `promptBoolOnce` (default `true`, only asked when the app is relevant to `.chezmoi.os`). `dev-server` skips the GUI prompts entirely and deploys only non-GUI/core tooling (git, shell, starship, nvim, tmux). `profile` is orthogonal to `.chezmoi.os` and to the DevPod Target's `devpod` flag — a separate axis for short-lived containers, narrower than `dev-server` (e.g. `devpod` excludes tmux; `dev-server` keeps it). Bootstrap Packages (git, mise, Docker, pwsh) stay profile-independent: they're prerequisites for chezmoi/dev work in general, not something a specific machine type would opt out of.

Git identity mapping is per actual usage, not a mechanical split: `personal` → `personal`+`work`; `dev` → `work`+`client`; `dev-server` → `personal`+`work`. Trade-off: up to five more prompts at `chezmoi init` time (one per GUI app) on `personal`/`dev`, and a `.chezmoiignore`/`.chezmoi.toml.tmpl` that's harder to read at a glance. Accepted because the alternative — always deploying every GUI app and every git identity to every machine — is exactly the "always the same setup" problem this change exists to fix.
